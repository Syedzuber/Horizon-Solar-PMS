## From the CEO card-fields build (2026-08-16)

- `projects/views.py` — `RESIDENTIAL_DESIGN_PHASE_ORDER = 3` / `RESIDENTIAL_DESIGN_TASK_ORDER = 1` is a POSITIONAL lookup for the Residential design task, and it is positional only because `Task` has no stable key (no `milestone_key`, no template FK, no slug). - **Django's `{# ... #}` comment cannot span multiple lines** — a multi-line one is not a comment at all, and any `{{ }}` inside it is parsed and executed. Fixed by switching to `{% comment %}`. Worth grepping the other templates for multi-line hash comments — this failure is silent, costs only queries, and nothing in the rendered page reveals it.
- Template drift across project vintages — active Residential projects carry 50, 51 or 52 tasks depending on when they were activated, and older ones still have a task literally named `Finance Confirmation` (e.g. `HRP-RES-2026-028`) where newer ones have `Pre Dispatch Payment Confirmation`. `(phase_order=3, task_order=1)` happens to be the `Design` task on all 26 today, but the drift shows positions are not guaranteed stable across vintages either. Relevant to the `_MILESTONE_TO_FINANCE_TASK` staleness noted above: on those older projects the stale name is the *correct* one, so fixing that map means handling both names, not swapping one for the other.
- Production data — `HRP-RES-2026-039` has all 51 tasks `Done` and design complete but is still `status='Active'` rather than `Commissioned`, so it occupies a CEO card as an active project with nothing left to do.

## From the shared approval primitive (Approvals S1, 2026-09-26)

- **Scope is now stored three different ways across three money-and-approval records.** `VendorOrder` stores it in explicit through-models: `VendorOrderSite` (project, plus a display-only `via_site_group`) and `VendorOrderProgram`, with no site-group relation of its own. `PaymentRequest` stores no scope; it reaches its scope through `vendor_order`, and its nullable `project` is a display anchor only (O2d). `ApprovalRequest` stores plain M2Ms: `programs`, `projects` and `site_groups`, each `related_name='approval_requests'`. Each choice was right for its own record, but any "everything touching tender X" reader now has to know all three shapes. Nothing reads approval scope yet.
- **A hard delete of a Project, Program or SiteGroup silently drops approval scope rows.** Django's auto-created M2M through tables CASCADE from both ends, so deleting a Project deletes its `projects_approvalrequest_projects` rows without a word, and the request no longer says it was about that site. Projects soft-delete in normal operation, so the exposure is the admin, a shell, or a future purge. `SiteGroup` CASCADEs from `Program` already, which makes a Program hard delete a two-level silent loss. `VendorOrderSite` and `VendorOrderProgram` are `PROTECT` for exactly this reason. Scope was ruled "for record only", so plain M2Ms were accepted knowingly; if the record must survive a hard delete, the fix is explicit through-models with `PROTECT`.
- **Session 4 must make the site-engineer candidate list real.** S1's `profile_can_be_approval_assignee(profile, 'site_engineer')` checks only for an active Site Engineer role. The spec's rule, "holds at least one task on the bill's project", needs `ContractorBillDetail.project`, which arrives in Session 4. Until then no caller creates a contractor bill.

## From approval notifications (Approvals 2b, 2026-09-27)

- Approval notices reach a Design Head's deputy; design change-request notices deliberately do not (D4). The two modules differ.
- **`transaction.on_commit(functools.partial(...), robust=True)` is not robust.** When a robust callback raises, Django 6.0.6 logs it with `f"Error calling {func.__qualname__} in on_commit() (%s)."` (`django/db/backends/base/base.py`, `run_and_clear_commit_hooks`). A `functools.partial` has no `__qualname__`, so the logging line itself raises `AttributeError` and the error escapes to the caller after the commit. `captureOnCommitCallbacks(execute=True)` has the same line. `approvals.py` registers lambdas for this reason. No other `on_commit` call in the codebase passes a partial today.
- **An approver whose step is superseded by another party's non-approval is not told.** When the PM requests changes on a material request, the Design Head's still-pending step is superseded at once (fail-fast), and nothing tells the Head their decision is no longer needed. Only the raiser hears (E2). The Head finds out from the request page or the next round's E1. Adding them would be one more recipient list in `approval_notices.after_decision`.
- **Fixed in 2b (same session):** the entry above about superseded approvers is closed. `approval_notices.after_decision` now tells each assignee whose pending, activated step a changes-requested or rejected close superseded, in-app only, with no deputies (`approval_step_superseded`).

The five PO/PI and payment paths now warn in that case (`submission_guard`); the approval raise form does not.
- **A GET whose key has already made a record is answered differently on the two families of forms.** On the five PO/PI and payment create paths, `submission_guard.already_submitted` redirects to the record with "This form was already submitted. You are viewing the record it created." and a link to a fresh form. `approval_views.approval_create` instead renders its form with an "already raised" state and no Raise button. Both stop the second record; the person sees two different screens for the same situation.
- **The order match's any-time "same vendor + same PO/PI number" rule is on hold** until the production query says whether one PO is legitimately recorded as several records. The rule that is built is the time window: same `created_by`, vendor and `total_amount` within 30 minutes, ruled out when both records carry a PO number (or both a PI number) and the numbers differ. A blank number never rules a match out. A second rule is one entry in `submission_guard.ORDER_MATCH_RULES`.
- **The payment match reuses `committed_total()` as `committed_total([p]) > 0`.** That reads "this payment counts" only because every payment's `effective_amount` is positive (`amount` is refused at 0 on entry, and a CHECK holds `approved_amount > 0`). If a zero-amount payment ever became possible, a counted payment would read as not counted. The proper fix is a shared per-payment predicate in `models.py` that `committed_total()` and `submission_guard.payment_duplicate` both call; `models.py` was outside this fix's scope.
- **The duplicate warning cannot keep chosen files.** It re-renders the form through the existing refusal path, which keeps every typed value and the key but not files (browsers will not restore a file input). On the three order forms, "Create anyway" therefore means attaching the PO/PI documents again; the existing "Attach the files again" banner says so.
- **Every keyed create form costs one extra query per load.** The five PO/PI and payment create forms now look up whether the URL's key has already made a record on every GET (`VendorOrder` or `PaymentRequest` by `client_uuid`). Accepted. `GroupRaisePageTests.test_the_raise_page_query_count_does_not_grow_with_site_count` pins the group raise page at 14 for this reason (was 13), measured on the keyed URL with the keyless redirect hop excluded.
- **`_assert_keyed_redirect` lives in `tests_vendor_order_raise.py`** and is imported by `tests_vendor_order_payments.py`, `tests_vendor_order_group.py` and `tests_purchases_workspace.py`. It is a shared test helper in a test module because the project has no shared test utility module; move it there when one exists.

## From material lines on approvals (2026-09-28)

- **PO/PI line pre-fill is deferred.** A pre-dispatch request's lines are typed by hand, although the PO/PI record it names already has `VendorOrderLine` rows. Pre-filling the lines table from them was out of scope by ruling. It would be a read in `approval_views._create_context` for the pre-dispatch kind; the chokepoint needs no change.
- **The unit list is enforced on approval lines only.** `projects/units.py` is the intended shared vocabulary, but `BOQItem.uom`, `BOQItemMaster.unit`, `VendorOrderLine` and `DCLineItem` units are still free text with no CHECK. Moving each onto `UNITS` needs a data audit of the values already stored (the `BOQItem.uom` drift is why the approval line has a CHECK).
- **The legacy request-wide fields stay on `MaterialApprovalDetail`.** `proposed_make`, `specification` and `quantity_note` are written by nothing now, but the 4 local approvals (all raised before lines) carry them and draw them under "Recorded before line items". No such request exists: approvals are not on Railway, and every round of the 4 local approvals has a snapshot.

The approval pages' own content, the lines table included, fits. `base.html` was outside this session's scope.
- **`0106_material_approval_lines` refuses to drop `boq_items` if any pick exists.** It found 0 rows in `solarpms_local`; on Railway the table is created empty by 0103 in the same deploy. A future database with picks would stop at 0106 with a message naming the table.
