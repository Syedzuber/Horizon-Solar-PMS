## From the CEO card-fields build (2026-08-16)

- `projects/views.py` — `RESIDENTIAL_DESIGN_PHASE_ORDER = 3` / `RESIDENTIAL_DESIGN_TASK_ORDER = 1` is a POSITIONAL lookup for the Residential design task, and it is positional only because `Task` has no stable key (no `milestone_key`, no template FK, no slug). It survives a rename and breaks on a reorder or an insertion into phase 3 of `build_residential_phases()`; the name-match alternative breaks on the opposite. This is the primary debt introduced by the card-fields session — if a stable key is ever added to `Task`, that constant pair is the call site to retire. Both subqueries carry their own `project_type` term so the position can never be read against an OPEX/CAPEX project.
- **Django's `{# ... #}` comment cannot span multiple lines** — a multi-line one is not a comment at all, and any `{{ }}` inside it is parsed and executed. A multi-line hash comment in `dashboard/ceo.html` warning *against* per-card relation lookups contained `{{ p.design_assignment.status }}` and `{{ p.phases.all }}` as examples, which Django executed once per card: 16 extra queries on an 8-project page, 52 on production's 26. Fixed by switching to `{% comment %}`. Worth grepping the other templates for multi-line hash comments — this failure is silent, costs only queries, and nothing in the rendered page reveals it.
- Template drift across project vintages — active Residential projects carry 50, 51 or 52 tasks depending on when they were activated, and older ones still have a task literally named `Finance Confirmation` (e.g. `HRP-RES-2026-028`) where newer ones have `Pre Dispatch Payment Confirmation`. `(phase_order=3, task_order=1)` happens to be the `Design` task on all 26 today, but the drift shows positions are not guaranteed stable across vintages either. Relevant to the `_MILESTONE_TO_FINANCE_TASK` staleness noted above: on those older projects the stale name is the *correct* one, so fixing that map means handling both names, not swapping one for the other.
- Production data — `HRP-RES-2026-039` has all 51 tasks `Done` and design complete but is still `status='Active'` rather than `Commissioned`, so it occupies a CEO card as an active project with nothing left to do.

## From the CEO card corrections (Session 1b, 2026-08-16)

- `Task` has **no dependency field, no predecessor FK and no concurrency flag**, so the schema cannot express which open tasks are actionable now. This is why the Session 1 "Next task" field was removed rather than repaired: ordering by `(phase_order, task_order)` names the *oldest skipped* task, not the next one (`HRP-RES-2026-037` read `Next: Advance Payment Confirmation` at 49 done / 1 pending). Any single-valued "next" on this schema is inference presented as fact. Adding a real one means a dependency model, not a better `order_by`.
- `Task.completed_at` coverage is **100%** — 0 nulls across all 492 `Done` tasks in production (467 in active-project scope). The historical write-path risk the Session 1b brief anticipated does not exist in this data, so "Last activity" under-reports nothing. Worth re-checking if a bulk status-update path is ever added, since `views.py:6452-6456` already does `Task.objects.filter(...).update(status=Task.DONE, completed_at=timezone.now())` — a future bulk `.update()` that omits `completed_at` would silently break this field.
- Production data — **12 of 28 active projects have never completed a single task**, so their cards read `Last: —`. Half the active portfolio has no recorded progress at all; the empty state is honest, but it is worth knowing that it is the second-most-common reading on the board.
- `DeliveryChallan.REJECTED` exists in `STATUS_CHOICES` but **no row in production has ever held it** (6 challans: 4 Expected, 1 Partially Received, 1 Received). The Material pill's red `Rejected` branch is therefore correct-by-construction but has never rendered against real data.
- Only **1 of 28** active projects has any delivery challan at all, so the Material row is absent from 27 of 28 cards. Intended per spec, but it means the SCM module is effectively unused on live projects rather than partially used.

## From the Top People card (Session 2, 2026-08-16)

- `projects/views.py` — the **Open** view does not exclude `is_active=False` assignees, while the new Completed and Usage views do. The Session 2 brief required the exclusion in all three views but also forbade rewriting the Open queryset; the shipped filters were left untouched and the asymmetry recorded here instead. Currently **inert**: zero inactive users hold an open task or have logged activity on production. It becomes visible the first time someone with open work is deactivated — that person would keep appearing in Open but not in Completed.
- `projects/views.py` — the **Usage** view is deliberately NOT context-filtered, unlike Open and Completed. `ActivityLog.project` is nullable and a large share of rows carry none (logins, program- and catalogue-level events), so filtering by project type would drop most of a person's activity and make the Tenders tab read as near-zero usage. Consequence: on the Tenders tab, Open and Completed are tender-scoped while Usage is portfolio-wide. Defensible but worth knowing before anyone reads the three views as directly comparable on that tab.
- **The Top People card changes height between views on the Tenders tab.** The two active tender sites have no tasks at all, so Open and Completed render "No activity in this period." while Usage renders 5 rows. The Session 2 brief asked for a fixed 5 rows per view *and* for short lists not to be padded with zero rows; those conflict, and the no-padding edge case was followed. On the EPC Residential tab all three views are 5 rows and the card is stable.
- Production data — the top 5 users account for **89.7%** of all logged activity in the last 30 days, and one user alone for 56.3%. 46 of 64 active accounts logged nothing at all. Adoption, not workload distribution, is what this card is actually measuring right now.
## From the task-derived Delivery and BOQ fields (Session 1c, 2026-08-16)

- **`Delivery` and `BOQ` on the CEO card are task-derived proxies, not records of the thing they name.** `Delivery` reports whether the five Delivery-phase tasks were ticked, not whether material physically arrived. `BOQ` reports whether the `BOQ Preparation` task was ticked, not whether a BOQ document exists. A project can show `Delivery: Done` with no `DeliveryChallan` row at all, and `BOQ: Done` with no `BOQ` row — on current production data, most of them do.
- **`DeliveryChallan` remains the semantically correct source for delivery status**, and `BOQ`/`BOQItem` for BOQ status. They were not used because production holds 1 challan and 2 BOQ rows across 28 active projects, so a card built on them renders blank on 27 of 28. Once the SCM workspace is genuinely populated, these two fields should move to the real models — at which point the task-derived and challan-derived answers will disagree on historical projects, and that disagreement is not a bug in either.
- Both fields inherit the **positional fragility already logged for the `Design` field**: `RESIDENTIAL_DELIVERY_PHASE_ORDER = 6` and `(RESIDENTIAL_BOQ_PHASE_ORDER, RESIDENTIAL_BOQ_TASK_ORDER) = (3, 5)` are positions in `build_residential_phases()`, not stable keys. They survive a rename and break on a reorder or an insertion. There are now three call sites keyed on template position; if a stable key is ever added to `Task`, all three retire together.
- There is **no OPEX/CAPEX phase template anywhere in the codebase** — `attach_residential_template` is the only builder, non-Residential activation instructs the PM to add tasks by hand, and no non-Residential project on production has a single `ProjectPhase` row (including Drafts). Both fields therefore hide on tender cards. If a tender template is ever added, these positions must not be assumed to carry over.
- `projects/templates/base.html:97-98` already documents the multi-line `{# #}` hazard recorded under Session 1b ("Multi-line comments MUST use `{% comment %}`; Django's `{# #}` is single-line only and otherwise renders straight onto the page"). The rule was known and written down before Session 1 broke it — worth surfacing that note somewhere more discoverable than one template's header comment.
